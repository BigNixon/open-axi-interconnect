    Contributing to Open AXI Interconnect¶

    Welcome¶

    Thank you for your interest in contributing to the Open AXI Interconnect project! This document provides guidelines and procedures for making contributions to ensure a smooth collaboration experience while maintaining project quality and consistency.

    Code of Conduct¶

    Our Pledge¶

    We pledge to foster an open and welcoming environment where all participants feel valued and respected regardless of: - Experience level - Background or identity - Technical expertise area - Communication style

    Our Standards¶

    Positive behavior includes: - Using welcoming and inclusive language - Being respectful of differing viewpoints - Gracefully accepting constructive criticism - Focusing on what is best for the community - Showing empathy towards other community members

    Unacceptable behavior includes: - Use of sexualized language or imagery - Personal or political attacks - Public or private harassment - Publishing others' private information without permission - Other conduct inappropriate in a professional setting

    How to Contribute¶

    Ways to Contribute¶

    You can contribute in several ways:

    1. Code Contributions
    2. Bug fixes
    3. New features
    4. Performance improvements

    5. Code refactoring

    6. Documentation Improvements

    7. Clarifications and corrections
    8. New tutorials or examples
    9. Translation efforts

    10. API documentation enhancement

    11. Issue Reporting

    12. Bug reports
    13. Feature requests
    14. Enhancement suggestions

    15. Usability feedback

    16. Community Support

    17. Answering questions
    18. Helping new users
    19. Reviewing pull requests
    20. Participating in discussions

    Getting Started¶

    1. Fork the Repository
    2. Navigate to the Open AXI Interconnect repository
    3. Click the "Fork" button in the upper right corner

    4. Clone your fork locally: git clone https://github.com/YOUR_USERNAME/open-axi-interconnect.git

    5. Set Up Development Environment

    6. Install required tools (refer to README.md)
    7. Set up upstream remote: git remote add upstream https://github.com/open-axi-interconnect/open-axi-interconnect.git

    8. Create a feature branch: git checkout -b feature/your-feature-name

    9. Make Your Changes

    10. Follow coding standards outlined below
    11. Write/update tests as needed
    12. Update documentation

    13. Commit your changes with clear messages

    14. Test Your Changes

    15. Run the complete test suite: cd sim && make
    16. Verify lint-free code: cd sim && make lint
    17. Check assertion syntax: cd sim && make lint-assertions

    18. Confirm coverage targets maintained

    19. Submit Your Contribution

    20. Push to your fork: git push origin feature/your-feature-name
    21. Create a Pull Request on GitHub
    22. Respond to review feedback promptly

    Pull Request Process¶

    Before Submitting¶

    Ensure your pull request: 1. Follows the project's coding standards 2. Includes appropriate tests for new functionality 3. Updates documentation as needed 4. Passes all automated checks 5. Has clear, descriptive commit messages

    Pull Request Requirements¶

    1. Description
    2. Clearly explain the problem being solved
    3. Describe the solution implemented
    4. Include references to related issues

    5. Detail any breaking changes

    6. Testing

    7. All existing tests pass
    8. New functionality includes tests
    9. Coverage metrics maintained or improved

    10. Performance impact assessed if relevant

    11. Documentation

    12. Code comments updated
    13. User documentation updated
    14. API documentation updated if applicable
    15. README changes if necessary

    Review Process¶

    1. Automated Checks
    2. Code linting passes
    3. Tests execute successfully
    4. Coverage thresholds maintained

    5. Documentation builds correctly

    6. Manual Review

    7. Code quality assessment
    8. Design appropriateness
    9. Test adequacy

    10. Documentation clarity

    11. Approval and Merge

    12. At least one maintainer approval required
    13. All feedback addressed
    14. CI/CD checks pass
    15. Merge by maintainers only

    Coding Standards¶

    SystemVerilog Guidelines¶

    1. Formatting 

      // Good: Consistent indentation and spacing
module example_module #(
    parameter WIDTH = 32
)(
    input  logic             clk,
    input  logic             rst_n,
    input  logic [WIDTH-1:0] data_in,
    output logic [WIDTH-1:0] data_out
);

    2. Naming Conventions

    3. Signals: lower_snake_case
    4. Modules: lower_snake_case
    5. Parameters: UPPER_CASE

    6. Instances: u_module_name

    7. Documentation

    8. Header comment for each module
    9. Inline comments for complex logic
    10. Parameter explanations
    11. Signal purpose descriptions

    Python Guidelines (Cocotb Tests)¶

    1. Function Naming 

      # Good: Descriptive test names
@cocotb.test()
async def test_uart_transmit_character(dut):

    2. Code Structure

    3. Import statements at top
    4. Constants grouped logically
    5. Helper functions before test cases

    6. Clear test case separation

    7. Error Handling 

      # Good: Meaningful assertions
assert data == expected_value, f"Expected {hex(expected_value)}, got {hex(data)}"

    Documentation Standards¶

    1. Markdown Formatting
    2. Use consistent heading levels
    3. Proper code block formatting
    4. Clear table structures

    5. Appropriate emphasis (bold/italic)

    6. Content Quality

    7. Accurate technical information
    8. Clear, concise language
    9. Practical examples
    10. Logical information flow

    Testing Guidelines¶

    Test Development¶

    1. New Functionality
    2. Create corresponding test cases
    3. Cover normal and error conditions
    4. Validate boundary cases

    5. Ensure adequate coverage

    6. Existing Tests

    7. Maintain compatibility
    8. Update when behavior changes
    9. Extend rather than replace when possible
    10. Preserve test case intent

    Coverage Requirements¶

    Contributions should maintain or improve: - Functional coverage: ≥95% - Statement coverage: ≥90% - Branch coverage: ≥90% - Toggle coverage: ≥90%

    Documentation Guidelines¶

    Content Structure¶

    1. Introduction
    2. Clear purpose statement
    3. Audience identification

    4. Prerequisites listing

    5. Body

    6. Logical progression of concepts
    7. Practical examples
    8. Visual aids where helpful

    9. Cross-references to related content

    10. Conclusion

    11. Summary of key points
    12. Next steps or related topics
    13. Feedback mechanisms

    Writing Style¶

    1. Clarity
    2. Use active voice
    3. Define technical terms
    4. Avoid ambiguous language

    5. Provide context for examples

    6. Consistency

    7. Follow established patterns
    8. Maintain terminology consistency
    9. Uniform formatting application
    10. Standardized heading structure

    Issue Reporting¶

    Creating Effective Issues¶

    When reporting bugs or requesting features:

    1. Bug Reports
    2. Clear, descriptive title
    3. Steps to reproduce
    4. Expected vs. actual behavior
    5. Environment details

    6. Relevant logs or error messages

    7. Feature Requests

    8. Problem statement
    9. Proposed solution
    10. Use cases and benefits

    11. Alternatives considered

    12. Enhancement Suggestions

    13. Current limitation description
    14. Improvement proposal
    15. Impact assessment
    16. Implementation considerations

    Recognition and Credit¶

    Contributors are recognized through: - GitHub contributor list - Release notes mentions - Documentation credits - Community acknowledgments

    Maintainer Responsibilities¶

    Review Process¶

    Maintainers commit to: - Prompt initial response to contributions - Constructive, respectful feedback - Clear explanation of requested changes - Timely final disposition of pull requests

    Quality Assurance¶

    Maintainers ensure: - Consistent application of standards - Adequate testing coverage - Documentation completeness - Backward compatibility preservation

    Recognition Policy¶

    Contributor Acknowledgment¶

    All contributors are acknowledged: - In project documentation - In release announcements - Through GitHub contributor recognition - In community communications

    Special Recognition¶

    Significant contributions may receive: - Featured contributor spotlights - Speaking opportunities at events - Project ambassador status - Repository maintainer rights

    Conclusion¶

    Contributing to the Open AXI Interconnect project is a collaborative effort aimed at creating high-quality, accessible hardware design resources. By following these guidelines, you help ensure a positive experience for all participants while advancing the project's goals.

    Your contributions, whether large or small, are valuable to the community. Thank you for participating in this open-source endeavor and helping make hardware design more accessible to everyone.

    If you have questions about contributing or need clarification on any aspect of this guide, please reach out through GitHub Issues or Discussions.
